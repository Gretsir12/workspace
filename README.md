# Workspaces Backend

Бэкенд web-IDE на Go. Пользователь выбирает набор пакетов nixpkgs, бэкенд собирает под него Docker-образ, запускает контейнер и отдаёт его терминал в браузер по WebSocket. Рядом хранятся проекты и файлы пользователей.

## Быстрый старт

### Требования

- Go (версия из `go.mod`)
- Docker (доступный текущему пользователю, сокет по умолчанию или `DOCKER_HOST`)
- PostgreSQL
- `make`

### Запуск

```bash
make run
```

Цель выполняет `go mod tidy`, собирает `bin/backend` из `./cmd/` и запускает его. Сервер слушает `:8000`, все маршруты под префиксом `/api/v1`.

## Архитектура

Приложение собрано из модулей. Каждый модуль реализует интерфейс `platform.Module`, получает общие зависимости (`platform.Deps`: конфиг, подключение к БД) и сам регистрирует свои маршруты.

```
HTTP (chi) ──► handler ──► service ──► repository ──► PostgreSQL (go-pg)
                              │
                              └──► util.Docker ──► Docker Engine API
```

Слои внутри модуля:

| Слой | Ответственность |
|---|---|
| `handler` | HTTP и WebSocket: разбор запроса, ответ клиенту |
| `service` | бизнес-логика, оркестрация репозиториев и Docker |
| `repository` | доступ к БД (go-pg) |
| `models` | модели данных и валидация запросов |
| `util` | вспомогательный код, в том числе клиент Docker |

## Структура репозитория

```
.
├── cmd/                      # точка входа
├── internal/
│   └── platform/             # общая платформа: config, httpserver, module
└── projects/                 # модуль projects
    └── internal/
        ├── handler/          # project, file, workspace (WebSocket)
        ├── models/
        ├── module/           # сборка модуля, Routes, createSchema
        ├── repository/
        ├── service/
        └── util/             # Docker: сборка образов и терминал
```

## Модули

### Модуль projects

Проекты, файлы проектов и workspace (запуск окружения).

**Маршруты** (префикс `/api/v1`):

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/proj/{id}` | получить проект |
| POST | `/proj` | создать проект |
| GET | `/files` | получить файл |
| GET | `/files/{project_id}` | все файлы проекта |
| POST | `/files` | создать файл |
| PUT | `/files` | обновить файл |
| GET | `/ws` | WebSocket: открыть workspace |

Формат тел запросов и ответов REST: TODO.

**Workspace.** Основная функциональность модуля.

1. Клиент подключается к `/api/v1/ws` и первым сообщением отправляет `{"user_id":..., "project_id":..., "dependencies":[...]}`.
2. Бэкенд собирает образ на базе `nixos/nix` с указанными пакетами nixpkgs (ревизия nixpkgs зафиксирована в коде, поэтому окружение воспроизводимо) и присылает статусы и лог сборки.
3. После статуса `ready` сокет работает как терминал контейнера: бинарные кадры это ввод и вывод, текстовый JSON `{"cols":..,"rows":..}` меняет размер.
4. Закрытие сокета останавливает и удаляет контейнер.

Подробный протокол для фронтенда: документ **«Workspaces: WebSocket API для фронтенда»** (TODO: добавить ссылку или перенести в `docs/workspaces-ws.md`).

**Образы.** Тег образа детерминирован: хеш от базового образа, ревизии nixpkgs и отсортированного списка пакетов. Одинаковый набор зависимостей даёт тот же образ, повторная сборка берётся из кеша слоёв.

## Работа с БД

Схема создаётся при старте модуля (`createSchema`, go-pg `CreateTable` с `IfNotExists`). Порядок важен: сначала таблицы, на которые есть внешние ключи.

| Таблица | Назначение |
|---|---|
| `projects` | проекты |
| `files` | файлы проектов |
| `workspace_images` | собранные образы: хеш зависимостей, ревизия nixpkgs, тег, статус, `last_used_at` |
| `workspaces` | запущенные окружения: пользователь, образ, `container_id`, статус, `expires_at` |

Статусы workspace: `pending` → `running` → `stopped` или `failed`. Статусы образа: `building`, `ready`, `failed`.

`CreateTable IfNotExists` не изменяет существующие таблицы. После изменения моделей на dev-окружении таблицы нужно пересоздать, для постоянной работы нужны миграции (TODO).

## Разработка

```bash
make run          # сборка и запуск
go build ./...    # проверка сборки
go vet ./...      # статический анализ
```

Соглашения:

- Ошибки HTTP возвращаются через `httpserver.ResponseError` в формате `{"message": "...", "timestamp": "..."}`.
- После апгрейда до WebSocket писать в `http.ResponseWriter` нельзя (соединение захвачено). Ошибки отправляются через сокет тем же форматом `ErrorResponse`.
- Запись в WebSocket-соединение должна идти из одной горутины или под мьютексом (требование gorilla/websocket).
- Операции очистки после закрытия сессии (удаление контейнера, смена статуса в БД) выполняются со своим контекстом, а не с контекстом запроса.

## Решение проблем

**`docker pull nixos/nix:...` обрывается с `EOF`.** Нестабильное соединение с Docker Hub на длинных загрузках. Уменьшите параллельность (`"max-concurrent-downloads": 1` в `daemon.json`) и повторяйте pull в цикле:

```bash
until docker pull nixos/nix:2.24.9; do echo retry; sleep 3; done
```

**`relation "workspace_images" does not exist`.** Таблицы создаются в неверном порядке или `createSchema` завершился с ошибкой. Образ должен создаваться раньше workspace, а ошибку `createSchema` нужно проверять при старте.

**В логах `response.WriteHeader on hijacked connection`.** Где-то после апгрейда WebSocket используется `http.ResponseWriter`. Ошибки в этой фазе отправляются через соединение, а не через `httpserver.ResponseError`.

**Остались контейнеры с меткой `ide.managed`.** Автоматической очистки осиротевших контейнеров после падения сервера пока нет: `docker ps -a --filter label=ide.managed=true`, затем `docker rm -f`.
